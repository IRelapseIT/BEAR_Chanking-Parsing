# Реестр парсеров и проверка форматов в BEAR

Черновик README по текущему коду `BEAR_BGE_M3`. Описан маршрут загрузки через `POST /v1/documents`. Автономный PDF/OCR-пакет принимает PDF напрямую через CLI и проверяет его сигнатуру при запуске.

| Компонент | За что отвечает | Как реализовано сейчас |
|---|---|---|
| **Реестр парсеров** | Определяет, какие форматы поддерживает запущенный BEAR и какому обработчику передать файл. | `ParsingPipeline.parsers` хранит словарь «расширение → экземпляр парсера». `Services` дополняет его обработчиками установленных модулей через `extra_parsers`. Для загрузки список разрешённых расширений берётся из ключей того же словаря. При разборе парсер выбирается по расширению имени в нижнем регистре. [Реестр](../bear-text-beta/src/bear_text_beta/parsing.py#L250) · [Подключение обработчиков](../bear-text-beta/src/bear_text_beta/runtime.py#L36) |
| **Проверка формата и MIME** | Проверяет доступные признаки соответствия файла выбранному формату и записывает MIME-метку в контекст. | Проверки распределены между `FileValidator`, `ParsingPipeline` и самими парсерами. DOCX проверяется как ZIP с обязательными частями, PDF — по сигнатуре `%PDF-` с последующим открытием, текстовые форматы — по признакам бинарных данных и возможности декодирования. MIME для TXT, Markdown, HTML и DOCX заполняется по расширению. Для PDF в общем API остаётся значение из входного `DocumentContext`. MIME из заголовка части загрузки с содержимым файла не сравнивается. [Проверка файла](../bear-text-beta/src/bear_text_beta/file_validation.py#L79) · [Присвоение MIME](../bear-text-beta/src/bear_text_beta/parsing.py#L283) · [PDF-парсер](../bear-text-beta/src/bear_text_beta/unified_parsing.py#L23) |

## 1. Как работает реестр

В базовом составе `.txt` направляется в `TXTParser`, `.md` в `MDParser`, `.html` и `.htm` в `HTMLParser`, а `.docx` в `DedocClient`. Когда доступен пакет `bear_fusion`, конфигурация `Services`, используемая в `BEAR_BGE_M3`, заменяет обработчики Markdown и DOCX на `StructuredMarkdownParser` и `DOCXParser` и добавляет `.pdf` с `PDFParser`. Например, файл `REPORT.PDF` нормализуется до ключа `.pdf`. Если ключа в реестре нет, загрузка отклоняется. [Регистрация](../bear-text-beta/src/bear_text_beta/runtime.py#L36) · [Проверка расширения](../bear-text-beta/src/bear_text_beta/file_validation.py#L79)

У парсеров общий контракт `parse(data, context) → ParsedDocument`. У текстового PDF и скана одинаковый обработчик. Уже при разборе страницы PDF-парсер решает, извлекать текстовый слой или применять OCR. [Интерфейс парсера](../bear-text-beta/src/bear_text_beta/ports.py#L14) · [Постраничная обработка PDF](../bear-fusion-lab/src/bear_fusion/pdf_adapter.py#L192)

## 2. Какие проверки выполняются и когда

1. **API принимает файл и `DocumentContext`.** Перед постановкой задания проверяет структуру контекста, версию документа, обязательные идентификаторы и совпадение имени файла с именем в контексте. [API загрузки](../bear-text-beta/src/bear_text_beta/api.py#L50)
2. **`FileValidator` проверяет файл при сохранении.** Проверяет расширение по реестру. За то же чтение считает размер и SHA-256, сохраняет префикс длиной до 16 байт. По умолчанию лимит файла — 50 МиБ. Для DOCX на этом этапе проверяется начало ZIP `50 4B 03 04`. Для текстовых расширений нулевой байт в префиксе отклоняется, если нет BOM UTF-16/UTF-32. При ошибке загрузки сохранённый объект удаляется. [Код потоковой проверки](../bear-text-beta/src/bear_text_beta/file_validation.py#L50)
3. **Worker передаёт сохранённые байты в `ParsingPipeline`.** Повторно проверяются размер и SHA-256. DOCX должен содержать `[Content_Types].xml` и `word/document.xml`. Также действуют лимиты ZIP-элементов, распаковки и вложений. TXT, MD и HTML декодируются в текст. Базовый режим принимает UTF-8 и Unicode BOM. CP1251 доступна при явном включении для парсеров, которым передана эта настройка. HTML и Markdown могут содержать обычный текст, поэтому факт успешного декодирования сам по себе эти форматы друг от друга не отличает. [Проверка DOCX](../bear-text-beta/src/bear_text_beta/file_validation.py#L103) · [Декодирование](../bear-text-beta/src/bear_text_beta/parsing.py#L16)
4. **`PDFParser` проверяет сигнатуру перед разбором.** Например, HTML, переименованный в `report.pdf`, может пройти проверку расширения при загрузке и попасть в очередь. Worker отклонит файл при проверке `%PDF-`. Если сигнатура совпадёт, PDF-библиотеки дальше проверят, можно ли открыть документ. Успешный разбор возвращает `ParsedDocument`, который BEAR нормализует и передаёт в чанкинг. [PDF-парсер](../bear-text-beta/src/bear_text_beta/unified_parsing.py#L23) · [Вызов парсера и чанкинга](../bear-text-beta/src/bear_text_beta/runtime.py#L97)

```text
POST /v1/documents → проверка контекста
  → FileValidator → разрешённое расширение, лимиты, префикс, SHA-256
  → сохранение оригинала и постановка задания
  → worker → ParsingPipeline → обработчик из реестра по расширению
  → проверки формата и разбор → ParsedDocument → чанкинг
```

Граница текущей реализации проходит между **проверкой признаков ожидаемого формата** и **полноценной MIME-валидацией**. Если в задаче требуется сравнить заявленный MIME с типом, определённым по содержимому, и отклонить конфликт ещё при загрузке, эта часть остаётся к реализации. Сейчас расхождение только в `Content-Type` загрузки само по себе не является ошибкой.
